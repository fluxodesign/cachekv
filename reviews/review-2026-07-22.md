# Code Review: `cachekv` — 2026-07-22

Follow-up to [review-2026-07-18.md](./review-2026-07-18.md). Scope: the `cachekv/` package
(`db.go`, `pool.go`, `types.go`, `cipher.go`, `metrics.go`, `validation.go`) plus the `main`
entrypoint. `go build ./...` and `go vet ./...` are clean; the `-race` concurrency test passes.

## What improved since the last review

- **`errors.Is` / `errors.As` are now used.** `databaseExist` uses `errors.As(&EMetaKeyNotFound)`
  (db.go:872) and `getMetaEntry` maps `badger.ErrKeyNotFound` via `errors.Is` (db.go:150).
- **`globalStateMu` exists** and guards the public entry points `GetStorageObject`,
  `listDatabases`, `ListConfigurations`, `UpdateConfigurations`, and `Startup`.
- **`deriveKeyFromHash`** (cipher.go:203) is a proper improvement over the old ASCII-substring
  approach — for the `init` path.
- Context propagation into `batchInsertGeneric`, a metrics collector, graceful `Shutdown`, and
  startup validation are all in place.

Unfortunately the two headline items from the last review — key derivation and thread safety —
were only *partially* fixed, and the partial key-derivation fix introduced a **worse** bug.

---

## 🔴 Critical

### C1. Key DB cannot be reopened after a restart (confirmed, data-loss class)

`initKeyDb` and `openKeyDb` derive the keyring's encryption key by **two different, incompatible
methods**:

- `initKeyDb` → `deriveKeyFromHash(hash)` = the **raw 32 bytes** of the SHA-256 digest (db.go:328,
  cipher.go:203-215).
- `openKeyDb` → `extractString(hash, 32)` = the **first 32 ASCII hex characters** of that digest
  (db.go:394-398, cipher.go:167-180).

For the same file these produce different byte sequences. The keyring is created (encrypted) with
the first key, so a normal second startup — where `Startup` takes the `else` branch and calls
`openKeyDb` against an existing `lock.db` on a fresh (empty) connection pool — calls
`OpenDatabase(keyPath, extractString-key)`, and Badger rejects it with an encryption-key mismatch.
**The keyring, and therefore every secure database's key, becomes unreadable after restart.**

This is not hypothetical: `TestOpenKeyDbWithDirAndNoFiles` (db_test.go:589-591) *asserts* the error
string `"encryption key mismatch for already open database"` as if it were correct behavior. That
test is encoding the bug, which is why CI stays green.

**Fix:** use one derivation function in both paths. `deriveKeyFromHash` is the right one; delete the
`extractString` call in `openKeyDb` and replace it with `deriveKeyFromHash(hash)`. Then update
`TestOpenKeyDbWithDirAndNoFiles` to assert the DB opens, and add a genuine
init-then-reopen-in-a-fresh-process test (see Testing below).

### C2. Connection-pool reference leak in `GetStorageObject`

`GetStorageObject` calls `GetConnectionPool().Get(dbPath, …)` (db.go:497), which increments the
entry's `refCount`, but it **never calls `Release`** and returns no handle the caller could use to
release. Every invocation pins the connection with `refCount ≥ 1` permanently, so `scheduleCleanup`
can never close it (`entry.refCount == 0` is never true — pool.go:128).

Because `databaseExist` → `GetStorageObject` (db.go:870) discards its result, **every existence
check leaks a ref**, and `CreateDatabase` calls `databaseExist` first thing. Over time the pool
holds every path it ever touched open.

**Fix:** either have `GetStorageObject` `Release` before returning (the returned `*Storage` holds
its own `*badger.DB` reference), or give `Storage` a `Close()`/`Release()` that decrements the pool
and require callers to use it. Pick one model and apply it consistently.

## 🟠 High

### H1. Reads mutate state: `getMetaDbObject` writes an event on every read

`getMetaDbObject` calls `writeMetaEvent(EventTypeRead, …)` (db.go:237) on every call. It is invoked
by `GetEntry`, `InsertEntry`, `UpdateEntry`, `RemoveEntry`, and `BatchInsert`, so **every data
operation performs an extra encrypted write to the meta DB**. Consequences:

- Write amplification and latency on the hot path (a "read" is never idempotent).
- Reads fail outright during key rotation, because `writeMetaEntry` returns `errDbRotating`
  (db.go:120) — so a rotation can break unrelated reads.

**Fix:** don't emit an event on metadata reads (or gate it behind a verbose/audit flag). Audit of
*reads* at this granularity is rarely worth the cost.

### H2. Global state is still mutated without the write lock

`globalStateMu` guards the public getters, but several functions **write** the shared
`metaStorage`/`keyStorage` structs while holding only a read lock or no lock at all:

- `metaBatchInsert` assigns `metaStorage.db = pool.Get(...)` (db.go:618) with no lock.
- `copyMetas` assigns `metaStorage.db` and flips `metaStorage.rotatingKey` (db.go:689,696,751)
  with no lock.
- `openMetaDb`/`openKeyDb` assign `metaStorage.*`/`keyStorage.*` — they run under `Startup`'s write
  lock, but `copyMetas`/`metaBatchInsert` can run concurrently with readers holding only `RLock`.

The `-race` test stays green only because `TestConcurrentGlobalStateAccess` (race_test.go) exercises
a single pre-created DB and never triggers rotation or meta re-open concurrently. The data race on
`metaStorage.db`/`.key`/`.file`/`.rotatingKey` is real. `rotatingKey` in particular is read/written
as a plain `bool` across goroutines.

**Fix:** funnel all mutation of `metaStorage`/`keyStorage` through the write lock, and make
`rotatingKey` an `atomic.Bool` (or guard it with the mutex everywhere).

### H3. `copyMetas` discards the stream error and never commits the rotation

```go
err = stream.Orchestrate(context.Background())   // db.go:749 — result immediately overwritten
err = batchInsertGeneric(ctx, &values, newDb)    // db.go:750
```

The `Orchestrate` error is thrown away, so a failed read of the source data still proceeds to write
a (possibly empty/partial) new meta DB and reports success. Separately, `copyMetas` returns the new
file/key but **never updates `metaStorage.file`/`.key`** to point at the rotated DB, and clears
`rotatingKey` without persisting the switch — so the rotation's result is only wired up if the
caller does it, and no production caller does (only tests call `copyMetas`).

**Fix:** check the `Orchestrate` error before writing; on success, atomically swap
`metaStorage.{file,key}` under the write lock and persist. Add a failure test.

## 🟡 Medium

### M1. `Release` spawns a goroutine per zero-crossing while holding the lock

`Release` does `go p.scheduleCleanup(dbPath)` inside `p.mu.Lock()` every time `refCount` hits 0
(pool.go:113-117). Rapid acquire/release cycles spawn many timer goroutines for the same path
(each waits `timeout`). The `scheduleCleanup` guard is safe, but it's wasteful and unbounded.

**Fix:** a single background janitor with a `time.Ticker` that sweeps idle entries, instead of one
goroutine per release.

### M2. Shutdown reopens the meta DB after closing the pool

`Shutdown` runs `pool.CloseAll()` (step 3) and *then* `writeShutdownEvent` (step 4), which calls
`pool.Get` to reopen the meta DB after the pool's context has been cancelled (metrics.go:203-207,
229-252). That connection is `Release`d but never closed before `os.Exit`.

**Fix:** write the shutdown event *before* `CloseAll`, then close the pool last.

### M3. `GetStorageObject` swallows an open error

If `pool.Get` returns `err != nil` but a non-nil `db`, the function logs, skips the `return`, and
returns `storageObject, nil` — dropping the error (db.go:497-511).

**Fix:** return the error unless you deliberately intend to proceed with a degraded handle.

### M4. Dead / non-crypto key helpers

`extractString` still uses `math/rand` for padding (cipher.go:175). Once C1 is fixed it should be
deleted along with the now-unused `deriveKeyFromPrivateKey` and `generateSecureKey` (cipher.go:183,
193) — they're dead code that reads like a security surface.

---

## 🟢 Low / polish

- `Cache()` is an exported no-op returning `nil` (db.go:1161) — either implement or remove; a silent
  stub in the public API is a trap.
- `EMetaKeyNotFound.Error()` has two identical branches (types.go:86-89).
- `getMetaEntry` keeps a brittle `strings.Contains(e.Error(), "key not found")` fallback next to the
  correct `errors.Is` check (db.go:150-151) — the fallback is now redundant; drop it.
- `DefaultConfig` reads `metaStorage.file` without the lock (db.go:116).
- Many `writeMetaEvent` errors are dropped with `_ =`; fine for events, but the audit trail can
  silently lose entries.
- README is 19 bytes; exported functions have no godoc. (Same as last review.)

---

## Testing gaps that matter here

- **No init-then-reopen test in a fresh process/pool.** This is exactly the gap that let C1 ship.
  Add a test that runs `Startup`, closes/clears the pool *and the singleton* (as `setup`'s teardown
  does), removes nothing, then re-runs the open path and reads a previously written secure value.
- `TestOpenKeyDbWithDirAndNoFiles` currently asserts the *bug*; fix it alongside C1.
- The `-race` suite doesn't cover rotation or concurrent meta re-open (H2). Add a test that runs
  `copyMetas`/`metaBatchInsert` concurrently with reads under `-race`.

---

## Suggested order of work

1. **C1** — unify key derivation; fix the test that enshrines the bug; add a reopen test. (Highest
   risk: silent data loss on restart.)
2. **C2** — decide the pool ownership model for `GetStorageObject` and apply it.
3. **H1** — stop writing events on metadata reads.
4. **H2 / H3** — lock all `metaStorage`/`keyStorage` mutation; fix rotation error handling and commit.
5. Medium/Low cleanups.

Overall: the architecture and the newer subsystems (pool, metrics, shutdown, validation) are
reasonable, but two confirmed correctness bugs (C1, C2) block production, and the thread-safety work
started in the last cycle is not yet consistent. C1 in particular should be treated as urgent.
